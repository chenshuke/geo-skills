# 品牌 AI 诊断完整审计交付 Playbook

本文件只在用户明确要求原始回答、全部信源、Excel、PDF、PPT、技术编号或正式审计附件时读取。普通品牌诊断默认使用 `reader-first-html-report.md`，只交付面向企业负责人的 HTML，不执行本 Playbook 的 Excel/PPT 要求。

用于把 GEO 平台 Scheduled Indexing 上榜检测任务整理成可复核、可复测的完整审计材料。直接读取用户选择的现有任务，不要求用户重新生成问题或人工粘贴 AI 回答。

## 1. 交付目标

让阅读者能够回答四个问题：

1. 用哪些问题、哪些平台、什么口径完成诊断？
2. AI 是否知道品牌，并且能否准确说明品牌？
3. AI 在真实需求场景中是否会主动推荐品牌？
4. 每个结论能否回到原始回答和引用来源核对？

不得用漂亮排版掩盖证据不足。报告、Excel 和 PPT 必须使用同一批数据与同一套统计口径。

## 2. 平台任务数据源（默认）

先调用：

```bash
node geo-brand-diagnosis/scripts/platform_diagnosis_data.js --action list --limit 30
```

向用户展示可用任务，用户选择后调用：

```bash
node geo-brand-diagnosis/scripts/platform_diagnosis_data.js \
  --action export \
  --schedule-id <任务ID> \
  --json-out 原始数据/platform_diagnosis_<任务ID>.json
```

正式报告以用户选中的实际任务、实际问题、实际平台和实际回答数为准。不得为了凑“8题×4平台”删除、复制或虚构回答。

每条回答必须保留：`schedule_id`、`selected_run_id`、`answer_id`、`topic_id`、问题全文、AI 平台、完整回答、品牌命中、竞品、来源标题、来源 URL、来源域名和截图 URL（如有）。

独立 `/citations` 端点为空时，使用 `answers[].searchedSites` 作为来源记录；不得因为 citations 为空而丢弃 answers 内已有来源。

## 3. 标准 8 题矩阵（仅新建任务参考）

只有平台没有现成任务、用户明确要求新建诊断任务时，才建议使用 5 个识别题和 3 个推荐题。根据品牌事实替换方括号内容，不照抄示例品牌。

### 2.1 识别类 5 题

| 编号 | 诊断目的 | 通用问题模板 |
|---|---|---|
| Q1 | 公司与产品服务 | `[品牌]是做什么的？主要提供哪些产品和服务？` |
| Q2 | 主体、品牌、区域关系 | `[公司主体]、[品牌/研究院/分支]是什么关系？总部和分支分别在哪里？` |
| Q3 | 定位与目标人群 | `[品牌]主要服务哪些行业和哪些类型的企业/人群？核心定位是什么？` |
| Q4 | 细分场景能力 | `[品牌]在[重点细分行业/场景]能解决哪些具体问题？` |
| Q5 | 人员、案例与背书 | `[品牌]有哪些可以核实的负责人、专业团队、客户案例和第三方合作记录？` |

Q4 用于识别“把行业常识写成品牌既有能力”的风险。Q5 用于识别“自述、招聘、媒体、工商和第三方合作记录被混为一谈”的风险。

### 2.2 推荐类 3 题

推荐题默认不得出现品牌名，否则无法测试 AI 是否主动推荐。

| 编号 | 推荐场景 | 通用问题模板 |
|---|---|---|
| Q6 | 核心细分行业 | `[细分行业]企业想解决[核心问题]，有哪些专业机构/品牌推荐？` |
| Q7 | 区域需求 | `[城市/区域]做[服务]，有哪些公司/品牌值得推荐？` |
| Q8 | 高价值复杂场景 | `[目标人群]面临[扩张/融资/高客单/复杂需求]，应该找哪些机构/品牌？` |

推荐题至少覆盖“细分行业、重点区域、高价值场景”三个入口。没有明确区域业务时，将 Q7 替换为另一类目标人群或使用场景。

## 4. 测试矩阵和记录要求

默认平台：豆包、元宝、DeepSeek、千问。用户指定其他平台时按用户要求替换。

新建任务的推荐矩阵为 8 题 x 4 平台 = 32 条回答；读取现有任务时以实际任务为准：

- 所有平台使用完全相同的问题文本；
- API 版与网页端必须分开标记，不得混写为同一测试环境；
- 每条记录保留任务 ID、运行 ID、`question_id/topic_id`、问题全文、平台、执行时间、回答编号、完整回答、searchedSites/引用来源标题与 URL；
- 每个问题尽量新开会话，降低上下文污染；
- 原始 JSON 不得为了报告美观而改写。

没有拿到某平台回答时标记“未取得数据”，不得按失败、未推荐或未收录统计。

## 5. 两套判定模型

### 5.1 识别类回答

先判断是否提到品牌，再判断是否准确：

| 等级 | 判定标准 |
|---|---|
| 基本准确 | 核心主体、业务、定位和边界与可核实资料一致；没有重要虚构 |
| 部分准确 | 主线基本正确，但存在遗漏、模糊、过度推断或弱来源支撑 |
| 高风险或错误 | 主体认错、能力虚构、地址/人员/案例错误、把行业常识归因给品牌，或可能损害信任 |
| 无法判断 | 缺少足够品牌资料或公开证据，不能强行定级 |

“出现品牌名”只能计为提及，不能直接计为准确。

### 5.2 推荐类回答

逐条记录：

- 是否主动出现品牌；
- 出现位置或排序；
- 是否明确推荐，还是只在补充说明中提及；
- 推荐理由是否与品牌真实能力一致；
- 同时出现哪些竞品；
- 是否给出官网、门店、联系方式或其他转化路径。

推荐命中率使用“进入合理候选名单”的严格口径，不把搜索结果页出现、引用网页提到品牌或回答末尾泛泛补充算作推荐。

## 6. 信源分层

每个关键事实必须记录核对来源和可信层级：

| 层级 | 常见来源 | 使用原则 |
|---|---|---|
| 强证据 | 政府/工商公开信息、品牌官网、合作方官网、正式公告、权威机构 | 可用于确认主体、合作、资质和公开事实 |
| 中证据 | 主流媒体、行业协会、可信垂直媒体 | 可用于补充背景，关键事实仍应交叉核对 |
| 弱证据 | 自媒体、招聘页、聚合页、转载、企业自述 | 只能作为线索，不能单独证明团队、案例或能力 |
| 未核实 | 无法访问、无作者日期、内容互相转载、来源不明 | 不得写成确定事实 |

“AI 搜到了某网页”不等于“网页证明了回答中的全部结论”。必须把网页实际内容与 AI 的具体主张逐项对应。

## 7. 指标口径

至少输出以下指标，分母必须写清：

```text
品牌提及率 = 识别类中提到品牌的有效回答数 / 识别类有效回答总数
基本准确率 = 识别类中基本准确回答数 / 识别类有效回答总数
高风险率 = 识别类中高风险或错误回答数 / 识别类有效回答总数
主动推荐率 = 推荐类中进入合理候选名单的回答数 / 推荐类有效回答总数
```

不要把提及率写成认知准确率。除非公开公式和权重，否则不要用一个综合分数替代原始数据。

## 8. 报告结构

正式报告按以下顺序组织：

1. 封面：报告名称、品牌、任务名称、scheduleId、runId、数据时间；
2. 诊断问题：完整展示选中任务的实际问题，不强制限定为 8 题；
3. 方法与审计链：说明数据来自 GEO 平台 Scheduled Indexing，保留平台原文、回答编号、来源标题和 URL；
4. 核心结论：用业务语言说明“知道、说准、推荐”三层状态；
5. 数据总览：问题数、平台数、有效回答数、信源数及四个核心比例；
6. 回答质量矩阵：按 Q1-Q5 x 平台展示分级；
7. 原始证据：每组包含 AI 原话、回答编号、问题所在、风险解释、核对依据和来源；
8. 平台差异：描述不同平台稳定出现的错误方式，不以一次回答给平台贴永久标签；
9. 推荐缺口：展示 Q6-Q8 的推荐名单、竞品占位和品牌是否进入；
10. 信源结构：说明来源数量、重复情况、强弱证据比例和缺口；
11. 分阶段改进：知识库、公开内容、第三方信源、门店/官网/联系方式等承接；
12. 验收标准：同题同平台复测，使用可核对指标，不承诺固定排名。

每个“有问题”的结论后必须紧跟“证据是什么、为什么有影响、应补什么”。

## 9. Excel 完整证据附件

Excel 至少包含 6 个工作表：

### 8.1 诊断总览

字段：任务名称、scheduleId、runId、测试日期、平台、问题数、有效回答数、识别提及率、基本准确率、高风险率、主动推荐率、信源记录数、去重页面数、核心结论。

### 8.2 诊断问题

字段：问题编号、问题类别、问题全文、诊断目的、是否带品牌名、目标平台。

### 8.3 全部回答

字段：scheduleId、runId、回答编号、topicId、问题全文、平台、执行时间、完整回答、是否提到品牌、准确等级、是否主动推荐、出现位置、推荐竞品、事实错误、人工判断、核对依据、截图URL。

### 8.4 全部信源

字段：scheduleId、runId、回答编号、topicId、平台、来源序号、标题、URL、域名、articleIndexed、来源类型、可信层级、是否支持该主张、备注。

### 8.5 信源汇总

字段：域名、来源类型、出现次数、关联回答数、可信层级、是否品牌可控、风险与补强建议。

### 8.6 口径说明

写明数据范围、缺失数据处理、准确分级、推荐命中、信源去重和人工核验规则。

Excel 必须保留完整回答，不能只放摘要。长文本设置自动换行、顶部对齐和适当列宽；冻结表头并开启筛选。生成与检查 Excel 时使用表格技能，不要求学员安装 Python。

## 10. HTML、PDF 与 PPT

### HTML / PDF

- HTML 使用连续阅读布局，适配 Safari；
- 打印样式不得强制把每个章节拆成独立页；
- 页面在浏览器中自然衔接，由 Safari 手动导出 PDF；
- 表格过宽时优先调整结构和列宽，不缩到不可读；
- 不在正式材料中写“客户可核对”“客户会议版”等制作视角词汇，改为“原始证据”“诊断依据”“完整记录”。

### PPT

- PPT 是报告的演示提炼版，不复制整篇 HTML；
- 开头必须说明诊断问题和样本范围；
- 至少展示 2-6 组最有代表性的原始证据；
- 结尾使用阶段改进与可复核验收，不展示内部合作分工、渠道策略、筛选线索、会议决策或固定周期承诺；
- 只使用 JavaScript 版 `@oai/artifact-tool` 生成、编辑和合并；禁止使用 `python-pptx` 及其检测脚本；
- 通过 PPTX 结构检查、整套渲染、逐页视觉检查和占位符扫描验收。

## 11. 对外措辞规则

对外材料写给企业阅读者，不写给内部销售或制作人员。

必须删除或改写：

- “先建立信任再进入市场”等内部策略；
- “服务商、渠道合作伙伴、筛选客户、成交线索、线下沙龙”等合作计划；
- “合作分工、会议决策、客户会议版”等制作或谈判措辞；
- 没有依据的固定周期、固定排名、固定推荐概率和结果保证。

可以保留：

- 事实性“目标客户”“客户案例”等业务术语；
- “被信任、被推荐”等描述 AI 用户决策的正常表达；
- 带条件、可复测的阶段建议和验收目标。

## 12. 完整验收

- [ ] scheduleId、runId、任务名称、诊断问题、平台、样本数和测试时间完整；
- [ ] 原始数据来自用户明确选择的 GEO 平台任务；
- [ ] 每条来源都保留标题、URL、域名，并能通过 answer_id 关联回答；
- [ ] 原始回答数等于有效问题 x 有效平台，缺失项单独说明；
- [ ] 提及、准确、推荐三个指标没有混用；
- [ ] 每个重大问题都有原话、回答编号、核对依据和来源；
- [ ] 回答与信源能通过回答编号关联；
- [ ] 报告、Excel 和 PPT 使用相同数字；
- [ ] 推荐题不含品牌名；
- [ ] 对外材料不含内部销售和合作计划；
- [ ] HTML 在 Safari 中连续阅读正常；
- [ ] Excel 无公式错误，长文本可读；
- [ ] PPT 无占位符、空白页、裁切、异常换行和内部措辞；
- [ ] 未使用 `python-pptx`。
