# GEO 品牌 AI 诊断

## 目标

诊断报告首先是给人看的决策报告，不是 API 日志或数据审计底稿。

默认回答六个问题：

1. AI 是否认识这个品牌？
2. AI 能否清晰、准确地描述品牌是谁、做什么、适合谁？
3. AI 在用户没有指定品牌时是否会主动推荐？
4. 如果不推荐，主要原因是什么？
5. AI 推荐了哪些竞品，竞品凭什么占据位置？
6. 品牌接下来最应该解决哪几个问题？

事实准确、证据可追溯仍是底层要求，但默认不把技术字段和审计过程堆进正文。

## 两种交付模式

### A. 老板阅读版（默认）

适用于“做个品牌诊断”“看看 AI 是否认识/推荐我”“做一个 HTML 报告”等普通请求。

默认只交付：

```text
HTML/{品牌名}GEO品牌AI诊断报告.html
```

Markdown 可作为生成 HTML 的内部中间文件保留，但不要作为主要交付物强调。平台原始 JSON 可作为内部取数缓存保存，不主动展示。

默认不要生成：

- Excel、PPT、PDF、PNG；
- 独立 answers/citations 拆分文件；
- 大段完整 AI 回答；
- 全部来源清单；
- 面向用户展示的 scheduleId、runId、topicId、answerId、接口字段名。

只有当某个严重错误必须定位时，才在脚注或“证据说明”中放少量来源链接；技术编号仍不进入主阅读路径。

### B. 完整审计版（按需）

仅当用户明确要求以下任一内容时启用：

- 原始回答、全部引用来源、证据审计；
- Excel、PDF、PPT、完整附件；
- 任务编号、运行编号、回答编号；
- 正式留档、投标、法务核验或多方复核。

此时完整读取 `references/full-delivery-playbook.md`。不要因为用户说“完整诊断”“整套诊断”就自动生成 Excel；要以用户是否明确需要附件或审计材料为准。

## 默认数据源

优先使用 GEO 平台已有 Scheduled Indexing 上榜检测任务，不要求用户人工生成问题或粘贴回答。

调用任何平台 API 前，遵守 `../geo-config/SKILL.md`：读取 openKey、companyId、productId；默认值为 0 时列出公司和产品供用户选择并写回配置。

列出任务：

```bash
node geo-brand-diagnosis/scripts/platform_diagnosis_data.js \
  --action list \
  --limit 30
```

选择规则：

1. 只展示当前 productId 的最近已完成任务。
2. 如果只有一个与目标品牌匹配且已完成的任务，可直接使用，不必多问一次。
3. 有多个有效任务时，让用户选择任务名称；界面上可展示日期、问题数、平台和完成状态，不展示密钥或接口地址。
4. 未经用户确认不要触发新检测或 `run-now`。

导出选中任务：

```bash
node geo-brand-diagnosis/scripts/platform_diagnosis_data.js \
  --action export \
  --schedule-id <任务ID> \
  --json-out <项目目录>/07_监测分析/品牌诊断报告/原始数据/platform_diagnosis_<任务ID>.json
```

平台没有可用任务、没有权限，或用户明确要求新建问题时，才读取 `references/diagnosis-prompts.md` 的兜底流程。

## 分析方法

### 1. 先分清三件事

- **被认识**：回答提到了目标品牌。
- **被说清**：品牌主体、业务、客户、优势和边界描述准确，没有重要编造。
- **被推荐**：不带品牌名的需求问题中，品牌进入了合理候选名单。

三者必须分别统计。提到品牌不等于说准确，说准确也不等于会推荐。

### 2. 判断 AI 是否说清品牌

有品牌知识库或证据台账时，逐条核对识别类回答。若项目存在 `02_知识库/证据库/核心优势与可信证据库_*.md`，必须同时读取：事实知识库用于核对“AI 有没有说对”，优势证据库用于判断“AI 有没有抓住真正值得推荐的能力”，待补强证据清单用于避免把尚未证实的优势反过来当作诊断基准。

| 等级 | 大白话含义 | 判断标准 |
|---|---|---|
| 清晰准确 | AI 基本说对了 | 主体、业务、客户和边界与证据一致，无重要虚构 |
| 大体知道但不够准 | AI 知道一些，但会说偏 | 有遗漏、混淆、过度推断、过时或弱证据 |
| 明显错误或有风险 | AI 说错了，可能影响信任 | 主体认错、能力虚构、人员/地址/案例错误 |
| 暂时无法判断 | 品牌资料不够 | 明确列出需要补充的资料，不强行评级 |

没有品牌知识库时，只判断提及、推荐、竞品和来源结构，不强行判断事实准确。

诊断完成后，把新发现按类型回流：基础事实缺失写入信息补充清单；已经提出但证据不足的优势写入待补强证据清单；AI 频繁误读且已有强证据的事实，列为优先公开和内容强化项。

### 3. 判断为什么不推荐

不要只写“品牌知名度不足”。必须结合回答和公开证据，从以下方面找具体原因：

- AI 不知道品牌属于哪个明确品类；
- 品牌事实、主体或服务边界互相冲突；
- 缺少对应场景的案例、方法、交付物和结果；
- 缺少客户、合作方、协会、媒体等第三方证明；
- 竞品拥有更多区域页、榜单、案例、资质或场景内容；
- 品牌内容能介绍自己，却没有回答用户的选购、比较和决策问题；
- 推荐后缺少清楚的咨询与承接入口。

无法从数据证明的原因标记为“需要进一步核实”，不要写成定论。

### 3A. 找到真正的病根

不要把所有问题平铺成“原因清单”。每个关键问题都要拆成五层：

```text
现象：AI 具体出现了什么表现
证据：哪些回答、平台或公开资料支持这个判断
病根：造成多个现象的共同底层原因
影响：对用户信任、品牌理解或推荐的影响
验证：完成什么动作后，用什么同题复测来验证病根是否被修复
```

优先寻找能解释多个现象的共同原因。例如“主体关系混乱、服务能力被扩写、推荐题完全缺席”可能共同指向：真实能力和案例没有被统一成 AI 可稳定理解的品牌事实与场景证据。不要把“知名度不足”当作默认病根，除非数据能支持。

为每个病根标注证据等级：

- **已证实**：平台回答和品牌资料直接对应，事实关系明确；
- **高度可能**：多个表现指向同一原因，但仍需要一次针对性复测；
- **待验证**：只有合理推断，不能写成确定结论。

报告至少要有一张“病因诊断表”：`现象｜直接证据｜病根判断｜证据等级｜影响｜验证方法`。

### 4. 做真正有用的竞品分析

提取推荐类回答中的竞品，并按场景归组，不要只列一长串名字。至少说明：

1. 哪些竞品在多个平台或多个问题中重复出现；
2. AI 给它们贴了什么优势标签；
3. 它们依靠哪些内容或信源进入推荐；
4. 我方缺的不是“所有东西”，而是哪一项关键证据或内容；
5. 哪些竞品适合直接对比，哪些只是不同规模或不同牌照的替代方案。

### 5. 正确理解来源

- `brand_indexed=true` 只表示提到品牌，不代表事实准确。
- `searchedSites` 表示 AI 检索或引用过的网页，不代表网页支持回答中的全部主张。
- 工商和招聘页可以证明公司或岗位线索，不能自动证明专业能力和客户结果。
- 关键事实优先使用政府、工商权威信息、品牌正式页面、合作方官网、正式公告和可信媒体交叉核验。

## 默认报告结构

生成老板阅读版前，完整读取 `references/reader-first-html-report.md`。

正文顺序固定为：

1. **一句话结论**：直接告诉读者 AI 当前怎么看这个品牌。
2. **三个核心结果**：认识度、描述清晰度、主动推荐度；数字旁必须有大白话解释。
3. **AI 眼中的品牌**：说对了什么、说不清什么、说错了什么。
4. **最值得警惕的 3-5 个问题**：用短小真实例子说明，不展示技术编号。
5. **真正的病根**：用“现象｜证据｜病根｜证据等级｜影响｜验证方法”表格区分主因和伴随问题。
6. **为什么 AI 不推荐**：按病根和证据强弱排序，解释原因而不是泛泛归因。
7. **竞品分析**：场景、主要竞品、竞品优势标签、我方缺口。
8. **最先做的三件事**：只保留真正影响认识和推荐的动作，并对应病根验证。
9. **阶段行动**：现在先做、接着补强、持续完善，使用企业语言。
10. **说明**：测试平台、问题数量、测试日期、数据限制和少量代表来源，放在末尾。

报告正文通常控制在 2500-4500 中文字。信息较少时可以更短，不为凑篇幅重复结论。

## 写作要求

- 先说结果，再解释为什么，最后说怎么改。
- 用“AI 能不能说清函霖”而不是“语义稳定性评估”。
- 用“AI 没有主动推荐”而不是“品牌未进入推荐集合”。
- 每个专业指标后必须立刻翻译成一句大白话。
- 一个段落只说一件事；长表格尽量改为 3-6 行短表或分组列表。
- 默认不出现 API、schema、字段名、任务编号和回答编号。
- 不把 30 多条回答逐条复述；只选最能说明问题的 3-5 个例子。
- 不把“AI 检索过”写成“来源已经证明”。
- 不编造品牌事实、案例、资质、数据或竞品结论。
- 允许指出缺点、适用边界和资料缺口。
- 报告中的每条行动必须能对应前文发现的问题。

## 生成 HTML

先生成符合阅读版结构的 Markdown，再使用无 Python 依赖的 Node 脚本：

```bash
node geo-brand-diagnosis/scripts/render_geo_brand_diagnosis.js \
  --input <报告.md> \
  --output-dir <项目目录>/07_监测分析/品牌诊断报告/HTML \
  --title "{品牌名} GEO 品牌 AI 诊断报告"
```

默认只交付 HTML，不生成 PNG。报告必须放入项目标准目录 `07_监测分析/品牌诊断报告/HTML/`。

## 默认验收

交付前检查：

- [ ] 打开第一屏，10 秒内能看懂品牌当前最大问题；
- [ ] 有独立头部封面，包含品牌名、报告名、一句话诊断、测试范围和日期；
- [ ] 明确回答 AI 是否认识、是否说清、是否推荐；
- [ ] 清楚解释为什么不推荐，而不只是报一个百分比；
- [ ] 明确区分现象、直接证据、主病根、伴随问题和待验证推断；
- [ ] 至少给出一张病因诊断表，并为每个主要病根提供验证方法；
- [ ] 有按场景组织的竞品分析，不是竞品名字堆砌；
- [ ] 有 3-5 个真实例子，但正文没有技术编号污染；
- [ ] 行动建议能逐一对应诊断问题；
- [ ] 重要品牌事实都有依据，没有把行业常识写成品牌能力；
- [ ] HTML 层级清楚、字号可读、表格不横向溢出、链接可点击；
- [ ] 手机上正文和表格仍能阅读；
- [ ] 没有在用户未要求时生成 Excel、PPT、PDF 或冗余附件。
