# GEO 平台逆向分析（geo-platform-reverse）

> **技能名称**：geo-platform-reverse
> **用途**：系统分析各AI平台的引用机制、搜索策略和交叉验证逻辑，全量读取每个引用链接深度分析，积累可迭代的知识库
> **版本**：v2.0
> **更新日期**：2026-05-08
> **归属入口**：`geo-workflow-hub` > 9. 数据分析

---

## 核心理念

GEO优化的前提是理解"裁判"。每个AI平台都有独特的引用决策机制——它搜索什么、引用什么、忽略什么、需要多少独立来源才敢给出结论。这些机制不公开、不稳定、且因问题类型而异。

本技能的核心工作方式：

1. **用户提供完整数据**：包含用户问题、AI回答、引用来源（标题+链接）、品牌是否上榜等
2. **逐平台分批分析**：每次一个平台，每批 10-15 条数据，全量读取每个引用链接
3. **深度理解每个来源**：不只看域名，而是实际读取页面内容来判断来源特征
4. **知识库持续积累**：每次分析的结果追加到平台和行业知识文件中，越用越准

### 与 geo-evidence-chain 的区别

| 维度 | geo-evidence-chain | geo-platform-reverse（本技能） |
|------|-------------------|----------------------------|
| **分析视角** | 品牌视角（我的品牌被引用得怎样） | 平台视角（这个平台如何决定引用什么） |
| **分析深度** | 统计层面（数量、占比、indexed率） | 内容层面（实际读取每个引用页面） |
| **核心产出** | 证据链评分 + 发布策略矩阵 | 平台画像 + 域名知识库 + 行业洞察 |
| **数据来源** | GEO平台API | 用户提供完整数据 |
| **可迭代性** | 每次独立运行 | 知识库持续积累 |

## 触发场景

- 用户提供了某个AI平台的收录数据，需要分析其引用机制
- 需要了解某个AI平台引用了哪些类型的来源、为什么引用
- 需要逐平台对比不同AI的引用行为差异
- 新增了一个AI平台，需要建立其引用画像
- 需要基于历史分析经验，不断优化对平台引用机制的理解

## 推荐工作流

### 标准流程（逐平台分析）

```
用户："帮我分析 DeepSeek 平台的引用机制，这是数据（第一批）..."

1. 接收数据 → 解析结构
2. 逐条读取每个引用链接 → 深度分析页面内容
3. 输出本批分析结果
4. 更新知识库（域名档案 + 平台发现）
5. 用户："这是第二批数据..."
6. 重复 2-4，并对比前序批次的发现
7. 所有批次完成后 → 生成/更新平台画像
8. 用户："换豆包平台，这是数据..."
9. 重复 1-7（可复用已有的域名知识）
```

### 数据发送建议

| 建议 | 说明 |
|------|------|
| **逐平台发送** | 不同AI平台引用机制差异大，逐个分析更精准 |
| **每批 10-15 条** | 每批约 100-200 个URL，全量读取可控 |
| **同一平台分多批** | 每批发完后我输出中间结果，你确认后发下一批 |
| **标注行业和品牌** | 每次发数据时告诉我行业和目标品牌名 |

## 分析框架：全量深度分析

### 对每条记录的分析

#### 步骤1：读取每个引用链接

对记录中的每个引用URL，使用 Read 或 webReader 工具实际读取页面内容。

**读取目标**：
- 页面标题（实际标题，可能与引用标题不同）
- 页面正文核心内容（首段、关键段落）
- 页面类型判断（新闻/评测/榜单/论坛帖/百科/官网/电商等）
- 内容质量评估（是否有实质信息、是否为SEO灌水）
- 品牌提及情况（是否提到目标品牌、以什么方式提到）
- 发布时间（如果能从页面获取）
- 页面权威度信号（网站类型、内容专业度）

#### 步骤2：单条记录分析

对每条记录输出：

```
【记录N】{用户问题}
├── AI回答摘要：{100字以内}
├── 品牌上榜：{是/否}，{排名/提及位置}
├── 引用来源数：{N}个
├── 来源详细分析：
│   ├── 来源1：{域名} | {页面类型} | {质量评估} | {品牌提及} | indexed
│   ├── 来源2：...
│   └── ...
├── 引用模式判断：
│   ├── 来源类型分布：{专业平台X个、媒体X个、论坛X个...}
│   ├── 交叉验证特征：{多源佐证/单一来源/混合}
│   └── 内容与问题匹配度：{高/中/低}
└── 本条发现：{值得记录的特征或异常}
```

## 八维分析框架

在综合分析阶段，对每个平台执行以下 8 个维度的分析：

### 维度1：来源类型分布

基于实际读取页面后的分类（而非仅看域名），将所有引用来源分为 10 类：

| 来源类型 | 判断依据 | 分类规则 |
|---------|---------|---------|
| **专业垂直平台** | 页面为行业垂直站内容 | 域名匹配 + 页面内容确认 |
| **权威媒体/新闻** | 页面为新闻报道/媒体文章 | 域名匹配 + 内容结构确认 |
| **论坛/社区** | 页面为用户讨论帖 | 域名匹配 + UGC内容特征 |
| **自媒体/公众号** | 页面为公众号文章 | URL匹配 + 页面布局 |
| **评测/导购** | 页面为产品评测/导购 | 内容特征（对比、评分、推荐） |
| **百科/知识库** | 页面为百科词条 | URL匹配 + 内容结构 |
| **内容聚合/百家号** | 页面为聚合平台内容 | 域名匹配 + 内容特征 |
| **品牌官网** | 页面为品牌自有页面 | 域名匹配 |
| **视频平台** | 页面为视频内容页 | 域名匹配 |
| **问答/知道** | 页面为问答内容 | 域名匹配 + 内容结构 |

> **关键区别**：这里不是只看域名分类，而是**实际读取页面后确认页面真实类型**。因为有些聚合站的页面可能是新闻内容，有些新闻站的页面可能是SEO灌水。

### 维度2：交叉验证模式

分析该平台的"证据链强度"特征：
- 平均引用来源数
- 被采纳（indexed）vs 未采纳的来源特征差异
- 来源类型多样性要求
- 同一信息是否需要多个独立来源佐证
- 域名多样性

### 维度3：内容质量与匹配度

基于实际读取的页面内容，分析：
- 被引用的页面内容质量分布（高质量/中等/低质量SEO）
- 内容与用户问题的匹配程度
- AI 倾向引用的内容特征（结构化/数据化/有排名/有对比...）
- 页面内容长度与被引用概率的关系

### 维度4：时效性要求

- 被引用页面的发布时间分布
- 标题含年份 vs 不含年份的被引用率差异
- 新鲜内容 vs 历史内容的被引用率差异

### 维度5：引用格式与呈现方式

- 脚注式 / 内联式 / 卡片式 / 无标注
- 引用在回答中的位置（开头/中间/结尾）
- 引用密度（每100字回答中引用多少个来源）

### 维度6：问题类型→引用模式

将用户问题按类型分类，分析不同问题类型的引用差异：

| 问题类型 | 识别关键词 |
|---------|-----------|
| 品牌推荐 | 推荐/哪个好/什么牌子 |
| 品牌排名 | 排名/十大/TOP/排行榜 |
| 技术对比 | 对比/vs/和...哪个好 |
| 知识科普 | 怎么/如何/是什么/为什么 |
| 价格相关 | 价格/多少钱/性价比 |
| 品牌评价 | {品牌}+怎么样/好不好 |

### 维度7：权威信号分析

- .gov/.edu 域名的被引用情况
- 央媒 vs 地方媒体 vs 自媒体的被引用率差异
- 页面内容中的权威信号（数据引用、专家引述、官方数据...）
- 品牌官网页面是否被引用、引用时被如何使用

### 维度8：平台特异性行为

从实际数据中动态发现的独特行为模式：
- 该平台独有的引用偏好
- 与其他平台显著不同的行为
- 需要特别注意的"反直觉"发现

### 知识库更新规则

1. **每次分析一个批次后**：
   - 更新对应平台知识文件的"已验证域名档案"表格
   - 新发现的特征追加到对应章节（标注来源批次）
   - 新域名追加到 `domain-registry.md`
   - 已有域名如果有新发现，更新对应记录

2. **置信度升级规则**：
   - 1次分析发现 → "待验证假设"
   - 2次分析确认 → "观察中"（置信度：低）
   - 3次以上确认 → "核心特征"（置信度：高）

3. **冲突处理**：
   - 新发现与已有知识冲突时，保留两者，标注冲突
   - 累积更多数据后，多数方向一致的胜出

## 执行步骤（用户数据模式）

### 步骤1：接收并解析数据

1. 从用户消息中提取：
   - 平台名称
   - 行业
   - 目标品牌
   - 数据记录列表
2. 验证数据完整性：
   - 每条记录是否有必需字段
   - 引用来源是否有URL
   - 标注缺失字段

### 步骤2：读取知识库

读取 `GEO知识库/platforms/{platform}.md`（如果存在），了解已有的分析基础：
- 已分析过的域名（无需重新深度分析的域名）
- 已验证的特征（对比新数据是否一致）
- 待验证的假设（本轮重点验证）

### 步骤3：全量读取引用链接

对当前批次每条记录的每个引用URL，采用**三层读取策略**：

#### 第一层：已有知识跳过

如果该域名已在知识库中有详细档案，且最近30天内分析过：
- 快速确认：检查URL是否与已分析页面同域名 → 直接复用已有档案
- 同域名但不同路径：仍需读取（同域名下不同页面质量可能差异大）

#### 第二层：webReader 快速读取

对新域名或需要重新确认的URL，优先使用 `mcp__web_reader__webReader`：

```
mcp__web_reader__webReader(url, return_format="markdown", retain_images=false)
```

**适用**：大多数服务端渲染的页面（新闻站、百科、部分论坛）
**优势**：速度快，直接返回 Markdown 格式正文
**判断成功**：返回内容长度 > 200 字

#### 第三层：Playwright 浏览器兜底（全自动，无需用户确认）

当 webReader 失败（返回空/太短/403）时，使用 Playwright MCP（独立浏览器实例，完全自主控制）：

```
1. playwright_navigate(url=目标URL)
2. playwright_snapshot()  # 获取页面DOM快照
3. 如果页面需要滚动加载：playwright_evaluate(expression="window.scrollTo(0, document.body.scrollHeight)")
4. 再次 playwright_snapshot() 获取完整内容
```

**适用**：JS 渲染页面、反爬页面、需要滚动加载的页面、百家号/头条号等聚合平台
**优势**：完整浏览器渲染，**完全自主操作，不需要用户确认任何请求**
**注意**：
- 快照可能很大（100K+字符），需要分段读取关键部分
- 如果 Playwright MCP 未加载，降级使用 Chrome DevTools（需用户确认）
- 如果两者都不可用，标记为"无法访问"

#### 第三层备选：Chrome DevTools（需用户手动确认）

仅在 Playwright 不可用时作为备选：

```
1. mcp__chrome-devtools__navigate_page(type="url", url=目标URL, timeout=15000)
2. mcp__chrome-devtools__take_snapshot()
3. 如果页面需要滚动加载：mcp__chrome-devtools__evaluate_script(function="() => { window.scrollTo(0, document.body.scrollHeight); }")
4. 再次 take_snapshot() 获取完整内容
```

> ⚠️ Chrome DevTools 连接用户本地浏览器，每次导航需要用户确认。不适合批量读取，仅用于少量关键页面的精确分析。

#### 读取失败处理

| 情况 | 处理方式 | 标记 |
|------|---------|------|
| 404 | 直接跳过 | `无法访问-404` |
| 403/反爬 | Playwright 重试 | 成功则继续，仍失败→`无法访问-反爬` |
| 需要登录 | 标记并跳过 | `无法访问-登录拦截` |
| 内容为空 | Playwright 重试 | 仍失败→`无法访问-空内容` |
| 超时（>15s） | 标记并跳过 | `无法访问-超时` |
| 视频页/图片页 | 记录页面类型即可 | `非文本内容-视频/图片` |
| PDF文件 | 用 Read 工具读取 | 成功则提取文本 |

#### 读取信息提取（每个URL必须提取）

无论用哪种方式读取，对每个URL提取以下信息：

| 字段 | 说明 | 提取方式 |
|------|------|---------|
| **实际页面标题** | 页面 `<title>` 标签内容 | 快照/title元素 |
| **页面类型** | 新闻/评测/榜单/论坛帖/百科/官网/电商/视频/问答 | 基于内容+URL综合判断 |
| **内容质量** | 1-5分评估 | 基于正文内容的专业度、深度、结构 |
| **品牌提及** | 是否提及目标品牌 | 全文搜索品牌名 |
| **品牌提及方式** | 主动推荐/被动提及/仅列名/竞品对比 | 上下文分析 |
| **发布时间** | 文章发布日期 | 页面中提取 |
| **页面篇幅** | 短/中/长 | 正文长度判断 |
| **内容结构** | 是否有排名/对比、数据/评分/表格 | 结构特征识别 |
| **来源域名** | 父域名 | URL解析 |
| **读取方式** | webReader/Playwright/ChromeDevTools/知识库复用 | 记录读取方式 |

#### 批量读取效率优化

对于同一批次中的多个URL：

1. **同域名合并**：同一父域名的多个URL，读取2-3个代表性页面即可，其余推断
2. **并行读取**：webReader 调用可以并行（不等待前一个完成）
3. **浏览器串行**：Playwright/Chrome DevTools 操作必须串行（同一时间只能操作一个页面）
4. **进度汇报**：每读取完5-8个URL，向用户汇报进度（如"已读取 23/150 个URL..."）

### 步骤4：单条记录分析

对每条记录，结合AI回答内容和读取到的页面信息，输出单条分析（格式见上文"分析框架"）。

### 步骤5：批次汇总

输出批次汇总（格式见上文"分析框架"）。

### 步骤6：更新知识库

1. **域名档案更新**：
   - 新域名 → 追加到 `GEO知识库/domain-registry.md`
   - 新域名 → 追加到平台知识文件的域名表格
   - 已有域名但有新发现 → 更新记录

2. **平台特征更新**：
   - 新发现 → 按置信度规则追加到对应章节
   - 与已有知识一致的发现 → 增加确认次数
   - 与已有知识冲突的发现 → 标注冲突

3. **行业知识更新**：
   - 跨平台通用发现 → 追加到行业知识文件
   - 平台特定发现 → 追加到行业文件的对应平台章节

```
📊 本批概况：

```

当用户确认所有批次发送完毕时：

2. 执行八维分析框架
3. 生成/更新平台画像文件（保存到 `--output-dir`）
4. 输出综合分析报告
5. 最终更新知识库

## 注意事项

1. **URL 读取是核心**：不要跳过任何URL的读取。即使域名已知，也要确认页面实际内容（因为同域名下不同页面质量可能差异很大）
2. **三层读取策略**：webReader 优先（快）→ Playwright 兜底（全自动浏览器）→ Chrome DevTools 备选（需用户确认）→ 标记失败（诚实）
3. **逐平台分析**：强烈建议每次只分析一个平台的数据，不同平台混在一起会导致特征混淆
4. **知识库是活的**：每次分析都会更新知识库，越用越准确。建议定期回顾知识库中的"待验证假设"
5. **数据格式灵活**：用户不一定要严格按模板格式发送，只要包含关键字段（问题、回答、引用来源URL），技能就能处理
6. **批次间保持上下文**：同一平台的多个批次分析在同一对话中进行，后续批次可以引用前面批次的发现
7. **新对话如何继续**：如果开了新对话，技能会先读取知识库了解已有基础，然后在此基础上继续分析
8. **进度透明**：每读取完 5-8 个 URL 向用户汇报进度，让用户了解处理进展
9. **同域名优化**：同一父域名的多个 URL，读取 2-3 个代表性页面即可，不需要每个都读（除非indexed状态不同）
