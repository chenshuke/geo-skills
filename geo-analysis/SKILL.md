# GEO 数据分析（geo-analysis）

> **通用兼容**：适用于 Claude Code、Codex 和兼容 Agent Skills 的工具；建议完整安装同级 `geo-*` 技能，运行诊断请使用 `../geo-runtime/SKILL.md`。


> **和 geo-source-assets 的分工**：`geo-analysis` 负责证据链、平台偏好和报告分析；如果用户要把 `searchedSites` 长期沉淀成“引用源资产库”、判断我方/竞品/行业/媒体信源及补强动作，请路由到 `geo-source-assets`。

> **和 geo-knowledge 证据库的分工**：`geo-knowledge` 的核心优势与可信证据库回答“企业能够证明什么”；本技能的证据链分析回答“AI 实际引用哪些来源、这些来源如何影响回答”。分析发现新的品牌事实或优势线索时，只能作为待核验线索回流 `geo-knowledge`，不能因 AI 引用次数高就升级为 A/B 级企业证据。

## 两层分析路由

默认执行**快速分析**。只有用户明确要求深挖，或快速分析判断继续投入值得时，才执行**深度分析**。完整输入、输出和升级条件见 [两层分析规范](references/two-tier-analysis.md)。

### 快速分析（默认）

- 输入限定为单个“项目 × 问题 × AI 平台 × 监测批次”的 AI 回答，以及引用标题、URL、域名和已有来源分类。
- 不打开引用页面，不读取正文，不推断 AI 内部检索关键词。
- 输出必须直接回答：发什么内容、内容需要哪些可核验事实、优先发到什么平台、建议发布数量、多久后复测。
- AI 回答中的品牌推荐理由只能标注为“回答原文给出的理由”，不能表述成已证明的上榜因果。
- 数据不足时列出限制，并说明是否建议升级深度分析。
- 面向人阅读时，`summary` 必须先给自然语言结论，再给变化和下一步；建议使用 3—5 个短段落或 Markdown 列表。
- `summary` 不得出现 snapshot、artifact、analysisTrigger、externalJobId、externalRunId、JSON 键名、`null` 字段或内部 ID。技术编号、完整 URL 和原始回答放在详细数据，不放进用户摘要。
- 每条建议只表达一个动作，重点结论可以用 Markdown 加粗；避免把几十个来源逐条堆在摘要里。

### 深度分析（按需）

- 默认只选最多 8 个高价值来源，不全量读取二三十个页面；用户指定来源时以指定范围为准。
- 优先级综合考虑重复引用、跨问题引用、跨时间持续引用、来源权威度和竞争强度。
- 逐页保存读取状态、正文范围和定位信息；读取失败必须标记待核验，禁止补写证据。
- 输出品牌级结论、来源级证据、我方证据缺口、竞争判断和针对性方案；部分来源失败时结果必须标记 `partial`。
- 各 AI 平台独立分析，不能把豆包结论直接套用到 DeepSeek、Kimi 或 ChatGPT。

本技能集覆盖 GEO 项目从快速归因、按需深挖、引用审核、证据链评分、项目仪表盘监控到可视化导出的完整闭环。快速分析负责低成本生成投放决策；平台逆向和证据链分析仅在需要确认具体页面证据时深入读取高价值来源。

## 子技能总览

### 1. 证据链分析（geo-evidence-chain）

分析 AI 平台引用来源的分布规律，评估证据链完整性，生成精准的发布策略矩阵。

**触发场景**：收录监测完成后，需分析引用偏好、评估证据链完整度、确定发布渠道。

**核心框架（六步）**：
1. **数据采集**：先用 `scheduledIndexing.list/get` 选择计划，再调用 `scheduledIndexing.answers` 分页读取回答和引用来源；需要矩阵时调用 `scheduledIndexing.topicPlatformMatrix`，需要趋势时调用 `scheduledIndexing.topicStats` 与 `scheduledIndexing.metrics`
2. **来源分类**：通过域名模式匹配将引用URL分为8种类型（专业平台/权威媒体/论坛社区/自媒体/评测导购/百科/聚合内容/品牌官网），支持 `--platform-profiles` 导入动态画像替代硬编码表
3. **平台证据画像**：按平台分组计算来源分布、引用性格标签、Top域名、收录率
4. **证据链评分**：四维评分——多样性(30%) + 权威性(30%) + 收录率(25%) + 品牌存在感(15%)，综合评级 A/B/C/D
5. **缺口识别**：对C/D评级识别平台偏好类型缺失、收录率为零、权威来源缺失等缺口
6. **发布策略矩阵**：基于缺口+平台偏好生成"内容→渠道→平台"映射，按P0/P1/P2优先级排列

**关键参数**：
| 参数 | 说明 |
|------|------|
| `--company` | 目标品牌名，逗号分隔别名 |
| `--platform` | 筛选特定平台 |
| `--platform-profiles` | 导入平台画像文件（由 geo-platform-reverse 生成） |
| `--keyword-map` | 关键词映射表路径 |
| `--quick` | 快速模式：仅输出摘要+策略矩阵 |

---

### 2. 平台逆向分析（geo-platform-reverse）

通过用户提供的数据逐平台分批分析高价值引用来源，深度理解来源特征，积累平台和行业维度知识库。

**与证据链分析的区别**：证据链分析是品牌视角（统计层面），平台逆向是平台视角（内容层面，实际读取每个页面）。

**工作方式**：
- 用户分批提供数据（包含问题、回答、引用URL），每个问题与 AI 平台保持独立上下文
- 默认按价值选择最多 8 个来源；只有用户明确要求时才扩大范围
- 输出八维分析：来源类型分布、交叉验证模式、内容质量匹配、时效性要求、引用格式、问题类型映射、权威信号、平台特异性行为
- 分析结果持续积累到知识库（`07_监测分析/` 目录），越用越准

**知识库结构**：
```
07_监测分析/
├── 平台画像/{平台名}.md      # 平台引用机制知识（持续更新）
├── 行业洞察/{行业名}.md      # 行业跨平台洞察
└── domain-registry.md          # 全局域名档案
```

**三层URL读取策略**：webReader优先（快）→ Playwright兜底（全自动浏览器）→ Chrome DevTools备选（需用户确认）→ 标记失败

---

### 3. 引用品牌审核（geo-citation-brand-audit）

自动访问AI引用来源页面，判断是否与目标品牌/产品相关，浏览器优先、可解释、可迭代。

**判定标签体系**：
| 标签 | 含义 |
|------|------|
| `brand_direct` | 页面核心主题就是目标品牌 |
| `brand_related` | 主主题相关，对目标品牌有实质介绍 |
| `generic_with_brand_mention` | 泛行业内容，仅提到品牌 |
| `competitor_only` | 主体是竞品 |
| `irrelevant` | 无关 |
| `unknown` | 无法稳定抽取，待人工复核 |

**执行流程**：预处理输入 → 浏览器打开页面 → 提取标题/正文/证据 → 规则初判（高分/中分/低分/负分信号）→ 语义复核 → 结构化输出（含置信度、证据、是否需人工复核）

**迭代路径**：V1纯浏览器 → V2浏览器+关键词规则 → V3规则主跑+浏览器兜底 → V4半自动批处理

---

### 4. 方案同步（sync-geo-plan）

将 GEO 拓展词方案和标题方案解析后批量上传到飞书多维表格，支持增量更新。

**执行步骤**：定位MD文件 → 解析拓展词方案（提取核心词、15个拓展词、优先级、长尾问题）→ 解析标题方案（提取推荐标题）→ 合并数据 → 调用 `add_keyword` MCP工具上传 → 输出结果统计

**关键参数**：
| 参数 | 说明 |
|------|------|
| `--project` / `--brand` / `--type` | 项目、品牌、品牌类型（个人/企业/产品） |
| `--all` | 同步所有项目 |
| `--force` | 强制更新已有数据 |

**数据字段映射**：核心关键词、拓展词、优先级、品牌类型、长尾问题、推荐内容类型、推荐标题、目标平台、创作/发布状态、创建日期

---

### 5. 项目仪表盘（geo-project-dashboard）

为 GEO 项目创建/更新 Obsidian 原生 DataviewJS 仪表盘，支持全局管理视图和 PDCA 排名追踪。

**四种操作**：
| Action | 用途 |
|--------|------|
| `create` | 为指定项目创建仪表盘（自动检测项目成熟度） |
| `global` | 生成跨项目全局管理视图 |
| `update` | 更新已有仪表盘（新收录报告/新文章后） |
| `pdca` | 取最近两份收录监测报告进行排名对比追踪 |

**项目成熟度分级**：早期（无跟踪表）→ 中期（有跟踪表，无收录）→ 成熟（全链路7环节+AI平台率+断点分析）

**全链路流水线**：核心关键词 → 拓展关键词 → 用户问题 → 文章标题 → 内容创作 → 平台发布 → AI收录

**输出位置**：`00_项目概览/仪表盘.md`

## 统一执行流程

当用户调用本技能集时，根据需求路由到对应子技能：

```
用户需求判断：
├── "分析收录/逆向分析/发布策略"     → 默认快速分析
├── "深挖证据/逐页分析/竞品证据"     → 深度分析（geo-platform-reverse）
├── "审核引用来源/品牌识别"        → geo-citation-brand-audit
├── "同步方案/上传飞书"            → sync-geo-plan
├── "仪表盘/全局视图/PDCA"        → geo-project-dashboard
└── "截图/HTML转图片"             → html-to-png
```

**配置前置**：调用平台数据前先执行 `best-geo auth status`，并确认 CLI 返回的 companyId 和 productId；不读取旧凭证文件。

```
收录检测完成 ──→ 证据链分析 ──→ 生成发布策略
```

## 注意事项

1. 证据链分析依赖收录检测结果，需先运行收录检测
2. 平台逆向分析必须逐平台进行；深度分析默认最多处理 8 个高价值来源
3. 引用品牌审核需 Playwright/Chromium 环境
4. 项目仪表盘依赖 Obsidian Dataview 插件
5. 自动 HTML 转 PNG 已移除；分析报告优先交付 HTML，发布用封面/素材优先使用 GEO 平台 AI 图片生成，不依赖 SVG
6. 所有数据驱动的子技能建议定期重新分析，因AI平台引用偏好可能随时间变化

## 输出归位硬规则

分析报告必须直接写入项目标准目录：证据链报告放 `07_监测分析/证据链分析/`，PDCA 放 `07_监测分析/PDCA对比/`，平台画像放 `07_监测分析/平台画像/`，行业洞察放 `07_监测分析/行业洞察/`，仪表盘放 `00_项目概览/仪表盘.md`。
